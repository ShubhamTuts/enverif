# Enverif v1.4.1 — Agent Activity + Skill/Plugin Routing Hotfix Design

## Goal
Ship one backward-compatible patch release that fixes the shared-hosting `/skills/*` and `/plugins/*` 403 collision, removes the large inline Live Activity block from chat, makes runtime activity a global top-bar **Agent activity** experience, renders correctly in dark mode, uses real agent avatars when available, and preserves generic capability-driven runtime behavior.

## Constraints
- No vendor/agent hardcoding. No Emily/Gmail/Google Maps/plugin-specific branches.
- Keep persisted `AgentRun`, child runs, steps, approvals and runtime projections as the source of truth.
- Preserve existing owner/admin/member authorization. Skill/plugin management remains owner/admin only through `manage-integrations`.
- Preserve direct filesystem protection for private application directories.
- Do not add a second orchestration/runtime state store.
- No public-site/docs/release-site redesign in this patch.
- Release target: `v1.4.1` after branch and post-merge `main` verification pass.

## 1. Skill/plugin 403 routing fix

### Current defect
The root `.htaccess` forbids any URL matching `skills/` or `plugins/` before Laravel routing, so legitimate virtual routes such as `/skills/create`, `/skills/install`, `/skills/{id}/edit` and `/plugins/{plugin}/dependencies` can receive Apache 403 even for an admin.

### Design
Split filesystem protection from virtual application routing:
- Continue denying direct access to private internal directories/files.
- Do not use a blanket URL-prefix deny for `skills/` or `plugins/` that collides with Laravel routes.
- Route legitimate application URLs through `public/index.php` as normal.
- Keep Laravel `workspace.capability:manage-integrations` as the authorization boundary.

### Acceptance criteria
- Admin/owner can load Skill Create and submit Skill Install/Create through Laravel.
- Admin/owner can use plugin dependency/removal routes.
- Member remains denied by Laravel capability middleware.
- Direct requests for protected source/application files remain forbidden.

## 2. Global Agent activity control

### Top bar
Replace the chat-local Live Activity presentation with a global top-bar control labelled **Agent activity**.

The control:
- is visible anywhere inside the authenticated workspace;
- shows a compact running/waiting state/count derived from the runtime feed;
- opens the right-side activity drawer;
- does not navigate away from the current page;
- is separate from Action Center, while approval counts may also appear inside Agent activity.

The existing Action Center remains the durable all-workspace approval destination.

## 3. Remove inline Live Activity block from chat

The large inline activity box inside the transcript is removed. Chat returns to a clean flow:
- user message;
- compact working state;
- inline approval card only when a decision is actually required;
- final assistant response.

Observable execution detail moves into **Agent activity**. This prevents tool telemetry from taking over the conversation area.

## 4. Agent activity drawer

Rename **Run activity** to **Agent activity**.

The drawer renders persisted runtime information only:
- primary agent and all descendant/sub-agent runs;
- run status and timestamps;
- parent/child hierarchy;
- tool and connector/MCP steps;
- step status and risk classification;
- pending approvals with Approve/Deny actions;
- links to detailed run pages where useful;
- recent runtime events for the selected/current run tree.

No chain-of-thought or raw model reasoning is exposed.

### Run scope
When opened from a chat, the drawer shows that chat's latest durable run tree. When opened globally outside a chat, it uses the runtime feed to show active/recent workspace chat runs and allows the user to inspect the relevant run tree without leaving the page.

## 5. Real agent avatars

`RunProjection` and the global runtime feed will expose an authenticated avatar URL for each persisted agent when the agent record exists.

Rendering rules:
1. Use the real uploaded agent avatar through the existing `/agents/{agent}/avatar` route.
2. If no avatar exists or the agent record is unavailable, use the agent initial/Enverif fallback.
3. Child agents use their own avatar, not the parent's.

No image bytes or private file paths are exposed in projection JSON.

## 6. Dark-mode correctness

Runtime UI must use Enverif's existing global design tokens rather than undefined fallback tokens.

Use existing tokens such as:
- `--panel`, `--panel-strong` for surfaces;
- `--line`, `--line-strong` for borders;
- `--text`, `--muted` for text;
- `--good`, `--warn`, `--bad` for state colors;
- `--accent`, `--accent-soft` for active state.

The activity drawer, backdrop, cards, steps, approvals, toast, badges and destructive dialog must remain legible in both light and dark themes. No hardcoded white surface may override dark mode.

## 7. Runtime data flow

### Global runtime feed
Extend the existing `/runtime/feed` response rather than creating a new state system. It remains workspace/user scoped and supplies enough metadata for the top-bar Agent activity indicator and recent run list.

### Detailed projection
Use the existing `RunProjection` for one run tree. Add only presentation-safe metadata needed by Agent activity, such as agent avatar URL and human-readable timing/state fields.

### Polling
- Keep one lightweight global runtime-feed poll.
- Do not reintroduce duplicate high-frequency activity polling.
- Chat status remains responsible for live current-chat state.
- Detailed activity fetches happen on drawer open and while the inspected run is active, at a bounded cadence.
- Hidden tabs back off polling.

## 8. Approval behavior

Approvals stay durable and policy-driven.
- Inline chat approval cards remain only for approvals tied to the current chat.
- Agent activity shows pending approvals in context with the agent/run/step that created them.
- Action Center remains the global approval queue.
- Approve/Deny updates the durable approval record and refreshes the drawer projection.
- No tool `allow` pattern may bypass external-write/destructive approval policy.

## 9. Generic tool/plugin behavior

Agent activity labels are derived from persisted tool names and schemas:
- first-party tools;
- connectors;
- MCP tools;
- child-agent delegation.

The UI humanizes generic tool identifiers. It must not contain special-case code for specific connector brands or agents.

The existing agent-scoped connectors/skills/MCP run snapshots remain the authorization boundary for tool discovery and execution.

## 10. Files/components expected to change

Likely production files:
- `.htaccess`
- `resources/views/layouts/app.blade.php`
- `resources/js/runtime-ui.js`
- `public/assets/runtime-ui.js`
- `resources/css/runtime-ui.css`
- `public/assets/runtime-ui.css`
- `app/Http/Controllers/RuntimeFeedController.php`
- `app/Core/Agents/RunProjection.php`
- small related runtime controller/view changes only if required by tests
- `VERSION` and release metadata at final release step

No unrelated public website or documentation-site assets.

## 11. Regression tests

Add tests for:
- admin can reach/create/install Skills through Laravel;
- member remains 403 through capability middleware;
- plugin application routes are not intercepted by root `.htaccess`;
- protected physical application paths stay denied in shared-hosting HTTP smoke;
- Agent activity top-bar control exists and old inline Live Activity UI does not;
- dark theme runtime CSS uses existing Enverif tokens and does not fall back to white surfaces;
- `RunProjection` returns agent avatar URLs and complete parent/child run trees;
- global runtime feed exposes active/recent run metadata without secrets;
- approval actions remain visible/actionable in Agent activity;
- runtime source/public JS and CSS assets remain byte-identical;
- no duplicate high-frequency activity poll is reintroduced.

## 12. Release gate

Before release:
1. Focused regressions pass.
2. Full Laravel/standalone/frontend/shared-hosting/installer CI passes on the feature branch.
3. Review exact diff for vendor/agent hardcoding and unrelated changes.
4. Confirm `main` has not diverged; merge without force.
5. Full CI passes again on the exact merged `main` SHA.
6. Bump to `1.4.1`, build deterministic release artifacts/checksums, tag the verified release commit, and publish `v1.4.1` only if release verification passes.

## Non-goals
- New public-site design.
- New documentation site.
- Token-by-token model streaming.
- A second activity database/event bus.
- Exposing chain-of-thought/raw reasoning.
- Brand-specific tool routing.
