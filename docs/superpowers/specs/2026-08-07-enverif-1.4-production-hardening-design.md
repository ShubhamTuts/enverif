# Enverif 1.4 Production Hardening & Action Center Design

Date: 2026-08-07
Target: Enverif 1.4.0
Branch: `fix/chat-agent-sales-orchestration-20260807`
Status: Design review

## 1. Objective

Ship Enverif 1.4.0 as a backward-compatible, zero-data-loss production hardening release that preserves the current Laravel/shared-hosting architecture while making agent execution durable, inspectable, extensible and safe enough for real external actions.

This release combines the existing chat/agent orchestration fixes on this branch with the full production audit findings from current `main`.

The release must not rewrite the application. Existing primitives remain the source of truth: Workspace, Agent, AgentRun, AgentRunStep, Skill, ConnectorConnection, Plugin, MCP server, Workflow, Lead, Campaign, Approval, AuditEvent, ChatThread and ChatMessage.

## 2. Product invariants

1. Chat is a projection of durable runtime state, not a second orchestration engine.
2. External capabilities are discovered from contracts/manifests; chat never hardcodes integration brands.
3. A user refresh, closes the tab or opens a conversation tomorrow and still sees the same run tree, approvals, connector calls and outcomes.
4. Any external mutation must be attributable to a run/step and must not execute twice because of retries or overlapping workers.
5. Tenant-owned data fails closed when workspace context is absent.
6. Sensitive administration and approval decisions are protected by workspace capabilities/roles.
7. Disconnect/delete/uninstall are separate operations and destructive actions require explicit confirmation.
8. Runtime/UI claims reflect what Enverif adapters actually support, not merely what upstream providers advertise.
9. Existing 1.3.x data upgrades in place with no destructive migration.
10. Source, public assets, lockfiles, docs, package names and release metadata remain synchronized.

## 3. Extensible capability architecture

### 3.1 Generic capability vocabulary

The runtime will reason about normalized capabilities rather than vendor names.

Examples:

- `mail.search`
- `mail.thread.read`
- `mail.draft`
- `mail.send`
- `mail.reply`
- `repo.search`
- `repo.file.read`
- `repo.file.write`
- `repo.branch.create`
- `repo.pr.create`
- `calendar.read`
- `calendar.schedule`
- `crm.lead.read`
- `crm.lead.write`

Connector drivers expose concrete actions and normalized capabilities in metadata. ToolRegistry remains responsible for converting available connector/MCP/local actions into model tools.

### 3.2 Email is not hardcoded

No chat/orchestrator branch may contain logic such as `if gmail`, `if outlook` or `if smtp` to decide how to handle email.

Instead:

- Gmail advertises search/read/draft/send/reply as supported by its adapter.
- Outlook advertises the equivalent capabilities supported by Microsoft Graph.
- SMTP advertises send only.
- A future IMAP connector can advertise search/read without changing chat/orchestrator code.
- A future support connector can advertise normalized support/message capabilities in the same way.

The agent selects an available tool whose capability matches the job. Brand-specific transport stays inside the driver.

### 3.3 Future GitHub plugin

A GitHub connector/plugin can expose repository actions through the same contract without modifying chat. Example actions include repository search, file read/write, branch creation, issue read/reply and PR creation. Risk metadata controls approval policy.

### 3.4 Plugin trust boundary

External PHP plugins continue to be trusted server-side code in 1.4.0. The UI/docs must state this explicitly. Public marketplace-style one-click installation is not treated as sandboxed. Manifest validation, publisher/source provenance and dependency checks are hardened, but process isolation is out of scope for this release.

## 4. Chat runtime projection

### 4.1 Durable execution tree

Add a normalized runtime projection built from persisted AgentRun, AgentRunStep, parent/child runs, Approval and audit/action records.

The projection represents:

- primary agent
- delegated/sub-agent runs
- connector/plugin calls
- MCP calls
- workflow handoffs
- approval waits
- retries/resumes
- tool success/failure
- final outcome

The projection API returns stable event IDs/timestamps/status, not hidden model reasoning.

### 4.2 Live activity UX

The transcript remains clean and ChatGPT-like. While work is running, show concise observable execution events such as:

- Research Agent started
- Delegated to Code Review Agent
- GitHub: searched repository
- GitHub: read `CheckoutService.php`
- Tests: 27 passed
- Gmail: searched support thread
- Approval required: send reply

Do not expose chain-of-thought. Only show observable actions, inputs that are safe to show, tool/connector identity, status and redacted outcomes.

### 4.3 Run drawer/sidebar

Clicking the running state opens a right-side drawer on desktop and slide-over on mobile showing the full durable run tree:

- agent/sub-agent hierarchy
- current step
- connector/MCP/workflow activity
- start/end times
- success/failure/waiting status
- approval cards
- links to full run detail

The existing Run page remains available for deep diagnostics.

### 4.4 Refresh/reconnect behavior

Important UI state must be reconstructed from server records. JavaScript is never the source of truth. Polling may remain for shared-host compatibility, but it consumes the durable projection.

Multiple browser refreshes must not create duplicate messages, duplicate approvals or duplicate actions.

### 4.5 Chat concurrency

Protect one-active-run-per-thread with a server-side transactional lock/compare-and-set, not just UI disabling.

Final assistant-message creation must use a database uniqueness invariant or atomic upsert so concurrent status requests cannot duplicate the final assistant message.

Chat thread/message/run persistence is transactional; attachment filesystem writes use compensation cleanup when DB/run creation fails.

## 5. Action Center and approvals

### 5.1 Single approval source of truth

Reuse the existing `approvals` subsystem. Do not create a parallel chat approval table.

### 5.2 Inline approval cards

When the primary or any descendant run creates an approval, the parent chat displays it immediately with:

- agent/tool/plugin identity
- human-readable action summary
- risk level
- relevant safe/redacted payload preview
- Approve
- Deny
- Review details

### 5.3 Global Action Center

Add an in-app Action Center surface with:

- pending approval badge in global navigation
- toast/banner when a new approval appears while the user is elsewhere
- pending/approved/denied history
- links back to originating chat/run

No email-based approval notification is required for 1.4.0. Notification channels can become plugins/capabilities later.

### 5.4 Atomic decisions

Approval decision uses atomic conditional transition `pending -> approved|denied` inside a transaction. Only the request that wins the transition dispatches continuation.

Authorization is explicit: approval ability is a workspace capability, not merely workspace membership.

## 6. Delete, disconnect, uninstall and dependency safety

Standardize destructive lifecycle actions across connectors/plugins/models/MCP/agents/workflows/skills:

- Disable: reversible operational toggle.
- Disconnect: remove/revoke credentials/tokens while preserving configuration/history.
- Delete connection: delete configured connection after dependency review.
- Uninstall external plugin: remove plugin package only when no live dependencies remain, or require explicit migration/removal flow.
- Delete agent/workflow/model/MCP/skill: dependency-aware confirmation.

Before deletion, show affected agents, workflows, schedules or other references.

High-impact operations require an explicit confirmation dialog and are audit logged.

Model connection deletion must not leave dangling `agent.model_connection_id`; use a safe foreign-key migration/null-on-delete or block deletion while referenced.

## 7. Exactly-once external action safety

### 7.1 Queue consumption and timeout invariants

- Docker/performance workers consume `agents,default` as appropriate.
- `retry_after` must exceed the maximum job timeout with safety margin.
- Shared-hosting queue/tick behavior follows the same logical invariants.

### 7.2 Per-run locking

Agent and workflow continuation acquire a distributed per-run mutex before mutating run/step state.

### 7.3 Atomic step claim

A tool/workflow step must be atomically claimed before execution. A second worker cannot execute the same pending step concurrently.

### 7.4 External action execution records

Introduce a durable external-action execution identity tied to run + step + tool/action + idempotency key.

For providers supporting native idempotency, forward the key. For providers without it:

- persist intent before the request
- record provider response/external ID when known
- distinguish `completed`, `failed_before_send` and `unknown_outcome`
- never blindly replay an unknown mutating outcome
- require operator/manual reconciliation or provider-specific lookup before retry

### 7.5 HTTP retries

Automatic retries remain acceptable for safe/idempotent reads and model calls where appropriate, but mutating connector POST/PATCH/DELETE calls do not inherit a generic blind retry policy.

Provider-specific retry policies may retry only when the operation is provably safe/idempotent.

## 8. Workspace security and RBAC

### 8.1 Fail-closed tenancy

Tenant-owned models cannot execute scoped queries without WorkspaceContext. Explicit administrative code may opt out with a clearly named unscoped path.

Queue/console jobs set/reset workspace context before loading scoped relationships.

Add negative tests proving missing context fails closed.

### 8.2 Workspace capabilities

Define explicit capabilities at minimum for:

- manage models/secrets
- manage connectors/secrets
- manage MCP
- manage plugins/skills
- manage agents/workflows/schedules/campaigns
- decide approvals
- view audit history
- manage workspace members/settings

Map current owner/admin/member roles to these capabilities while leaving room for future custom roles.

### 8.3 Outbound endpoint trust / SSRF

Centralize outbound endpoint validation for:

- custom model base URLs
- MCP endpoints
- automation webhooks
- remote skill/plugin sources where applicable

Validate scheme, hostname, DNS result, redirects and resolved destination. Block loopback, private, link-local, metadata and other unsafe ranges by default. Revalidate redirect destinations to reduce DNS-rebinding/redirect bypasses.

Changing an endpoint that will receive a stored secret requires privileged capability and explicit confirmation/re-authentication/re-entry where appropriate so retained credentials cannot silently be exfiltrated to a new host.

## 9. Webhook security

Workflow webhooks are explicitly exempted from browser CSRF middleware only for the webhook route.

Replace static-secret-only trust with signed request support:

- HMAC over canonical body
- timestamp window
- nonce/event ID
- replay cache
- idempotency key

Preserve a documented compatibility path where necessary, but secure mode is the production default.

Add HTTP-level tests, not only engine tests.

## 10. Model/provider layer

### 10.1 Truthful capability registry

Model metadata represents capabilities implemented by the Enverif adapter. Do not mark streaming/files/tool support true merely because the upstream model supports it.

### 10.2 Capability gating

Before an agent run starts, validate selected model against required capabilities. If tools are attached, selected model must support tool calling. Attachments/files are gated by actual adapter/file-pipeline support.

### 10.3 Provider diagnostics

Connection testing returns structured diagnostics: authentication, endpoint connectivity, model availability, quota/rate-limit/billing/region/capability issues, provider request ID and safe remediation message. Secrets are redacted.

### 10.4 Dynamic model discovery

Use provider discovery where available with cached fallback catalog and support custom model IDs. Do not make application correctness depend on a stale hardcoded list.

### 10.5 Streaming

True token/event streaming is optional for 1.4.0 unless implemented cleanly across adapters. If not implemented, the registry/UI must not claim it as an available Enverif capability.

## 11. Files and context

Either implement real parsing for every file type advertised as readable or stop advertising unsupported formats.

Production file handling requires:

- magic-byte/MIME validation
- private storage
- safe extraction limits
- PDF/DOCX/XLSX parsing where accepted
- bounded extraction size
- chunking/artifact storage for large documents
- retrieval/context selection rather than dumping entire files into prompts

Context building becomes token-aware and model-aware. Tool results have byte/item limits, pagination/truncation metadata and artifact fallback for oversized output.

## 12. MCP and skill hardening

### 12.1 MCP

- per-agent MCP attachment/allowlist, matching connector assignment semantics
- local Enverif policy is authoritative for risk; remote MCP annotations are advisory only
- egress/SSRF validation
- bounded responses/timeouts
- capability/risk override UI

### 12.2 Skills

- instruction/content package only; no arbitrary executable PHP through the skill system
- archive compressed/decompressed size limits
- file-count/path limits
- immutable commit-SHA provenance where possible
- checksum verification
- quarantine/review before activation for remote installs
- scanner findings are advisory defense-in-depth, not a claim of sandboxing
- trusted-host configuration has one source of truth

## 13. Workflow runtime

- validate connector arguments against action parameter schema before activation
- save/update/activation is atomic; failed activation does not persist half-valid active changes
- exactly-once semantics follow external-action execution records
- safe retry/resume distinguishes immutable replay from 'run again with current configuration'
- workflow retry can replay stored definition/settings snapshot
- diagnostics are sanitized before user display

## 14. Agent retry semantics

Expose two distinct operations:

1. Retry original run: replay immutable run snapshot/context where safe.
2. Run again: use current agent/workflow configuration.

Do not label the latter as a retry.

## 15. Campaign engine

Campaigns may not be marketed as fully executable until a runtime exists that advances members.

1.4 production target includes a minimal reliable campaign executor if campaign execution remains a product claim:

- due-member worker
- sender/connector selection by capability
- step delays/timezone/business hours
- send/reply threading state
- delivery/activity recording
- suppression/unsubscribe
- bounce/reply stop conditions where available
- pacing/sending limits
- idempotent step execution

If all of this cannot meet release gates, the UI/docs must explicitly label campaigns as configuration/preview rather than a complete sending engine.

## 16. Lead/export safety

Neutralize spreadsheet formula prefixes in CSV export.

Preserve/extend source provenance and do not imply field-level provenance unless actually stored.

## 17. Installer and authentication hardening

Installer:

- one-time installation claim/bootstrap secret for fresh public installs
- safer staged `.env` writes with rollback/recovery
- no destructive assumptions about pre-existing user/workspace rows
- upgrade path tested against retained 1.3.x fixture
- provider setup diagnostics are optional/non-blocking

Authentication:

- login throttling/rate limits now
- 2FA/WebAuthn can remain future scope

## 18. Audit integrity

Describe audit data accurately as hash-linked/tamper-evident, not absolutely immutable.

Serialize per-workspace chain append or use a stronger append strategy so concurrent events cannot fork the chain.

External actions, approvals, connection lifecycle changes and destructive operations produce audit entries.

## 19. UI/design-system constraints

Keep the current visual language unless a global primitive is intentionally improved.

Do not patch individual pages with conflicting one-off CSS. Introduce/reuse global tokens/components for:

- spacing
- forms/actions
- buttons
- icon buttons
- drawers/modals
- status chips
- approval cards
- run activity rows
- destructive confirmations
- responsive layout
- focus/hover/disabled states

Use a consistent local UI icon system plus authentic integration assets/fallback. Chat must not hardcode third-party developer attribution.

Desktop and mobile behavior are release-tested.

## 20. Release engineering

1. Version is 1.4.0 consistently in VERSION, README, PRD/docs, changelog and release packaging.
2. Commit Composer/NPM lockfiles and make Docker/CI/release consume them.
3. Fix release archive filename/root-directory inconsistencies.
4. Preserve synchronized resource/public built assets.
5. Normal source remains on GitHub main; no bootstrap-only repository shape.
6. Shared-hosting ZIP and standard source ZIP use the same verified source revision.
7. No production-ready claim until defined gates pass.

## 21. Test/release gates

Required automated coverage includes:

- queue consumes agent jobs
- retry_after/timeout invariant
- overlapping same-run continuation
- atomic tool/step claim
- duplicate mutating HTTP prevention
- unknown external outcome handling
- concurrent approval decisions
- member vs admin authorization
- stored-secret endpoint exfiltration attempts
- fail-closed workspace context
- stale worker workspace context
- webhook HTTP/CSRF/signature/replay/idempotency
- chat concurrent sends
- unique final assistant message
- refresh reconstructs run tree and approvals
- descendant approval appears in parent chat
- connector disconnect/delete dependency confirmation
- email capability selection without vendor hardcoding
- Gmail/Outlook/SMTP capability differences
- model tool-capability gating
- provider diagnostic error mapping
- file MIME/extraction limits
- connector argument validation
- bounded tool results
- CSV formula neutralization
- campaign progression/idempotency if campaign engine ships
- fresh installer + 1.3.x upgrade fixture
- workspace isolation across routes/actions

Browser tests cover desktop/mobile chat, Action Center, approval flow, run drawer, attachment UX, theme, connector lifecycle and destructive confirmations.

## 22. Implementation order

1. Runtime/queue/exactly-once safety.
2. RBAC, fail-closed tenancy and egress security.
3. Approval atomicity + Action Center backend.
4. Durable chat run projection and run drawer.
5. Capability-based connector/email abstraction cleanup.
6. Delete/disconnect/uninstall lifecycle safety.
7. Webhook security.
8. Provider/model diagnostics and capability gating.
9. File/context/tool-result hardening.
10. MCP/skill hardening.
11. Workflow/retry correctness.
12. Campaign execution or explicit capability downgrade.
13. Installer/auth/audit/export hardening.
14. Global UI/design-system polish and responsive/browser tests.
15. Release engineering, docs, upgrade guide and final packaging.

## 23. Non-goals for 1.4.0

- rewriting Laravel as a separate SPA/backend
- sandboxing arbitrary third-party PHP plugins at OS/process level
- public plugin marketplace with one-click untrusted code
- email approval notifications
- exposing hidden chain-of-thought
- pretending provider streaming/file support exists when Enverif does not implement it

## 24. Definition of done

Enverif 1.4.0 is complete only when:

- all P0 audit findings covered by this design are fixed or explicitly removed from product claims
- all tests/release gates pass on the release revision
- no duplicate external action is reproducible under tested queue/retry races
- workspace security is fail-closed and role-protected
- chat reconstructs complete observable runtime state after refresh
- child-agent approvals surface inline and in Action Center
- email behavior is capability-driven rather than Gmail/Outlook/SMTP hardcoded
- destructive connector/plugin/API lifecycle actions require correct confirmation and dependency handling
- source/public assets and lockfiles are reproducible
- upgrade from supported 1.3.x data is verified without data loss
- standard and shared-hosting release artifacts are produced from the same verified revision
